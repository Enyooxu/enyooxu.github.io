Mysql中的索引

发表于2026-02-10|更新于2026-02-27|Mysql
|浏览量:

背景

在MySQL中，索引是一种用于加速数据查询的数据结构。本质上，它是对表中某一列或多列的值进行排序并建立结构化存储，从而避免全表扫描。可以把它理解为书的目录这样在查找的时候就不用一页页翻，只需通过目录即可快速定位。

索引分类

按数据结构划分

B+Tree索引

B+Tree 是一种多路平衡查找树。相比于普通的二叉树，它的每个节点可以拥有更多的子节点（通常成百上千），这让树变得“矮胖”。他有一下几点主要特征：

  • 非叶子节点【内部节点】： 仅存储索引键（Key）和指向子节点的指针，不存储实际的数据行。这使得每个节点能容纳更多索引，从而降低树的高度。
  • 叶子节点： 存储完整的键值对（Key + Data）。在聚簇索引中，Data 是完整的行记录；在非聚簇索引中，Data 通常是主键值。
  • 双向链表连接： 所有的叶子节点通过指针连接在一起，形成一个有序的双向链表。这对于范围查询至关重要。

工作原理：

例1：普通查找
假设我们要查找主键 ID 为 20 的记录：

  1. 从根节点开始： 比较 20 与节点内的键值，确定所在的区间。
  2. 逐层向下： 根据指针进入下一层索引页。
  3. 定位叶子节点： 到达叶子节点后，通过二分查找精确定位到 20 对应的行数据。

这里我一开始有个疑问，叶子节点明明是一个有序的双向链表，为什么是通过二分查找而不是沿着链表查找呢？
首先要说明的是Mysql的innodb是以页为存储单位的，每个B+Tree的叶子节点都是一个页的大小的倍数，默认一页的大小是16K。这里的每一个页都包含两个页指针，一个是previous page指针，指向上一个页，一个是next page指针，指向下一个页。头部还有Page的类型信息和用来唯一标识Page的编号。根据这个指针分布可以想象到Page链接起来就是一个双向链表。如下图所示:

由于一个B+Tree的叶子节点是一个页，所以每个叶子节点之间是一个双向链表的结构。如下图所示：

当用户从非叶子节点根据指针向下查找时，定位到的是一个具体的页。随后数据库会将这整个 16KB 的页从磁盘加载到内存中。一个 16KB 的页里可能包含了几百甚至上千行数据记录。至于页的组成可以参考下述文章中的介绍：MySQL 页完全指南——浅入深出页的原理

例2：范围查询
假设执行 SELECT * FROM table WHERE id BETWEEN 10 AND 30

  1. 先找到 id=10 的叶子节点。
  2. 利用叶子节点之间的双向指针【每个叶子节点都是一个页】，顺着链表向后遍历，直到遇到 id=30 的节点。这样就无需重新回到根节点进行搜索。

哈希索引

工作原理：
Hash 索引建立在哈希表的基础上。当你为某一列（例如 User_ID）创建 Hash 索引时会执行以下几步：

  1. 计算哈希值：数据库对该列的每一个值应用哈希函数（如 CRC32 或内置算法），生成一个哈希码。
  2. 存储映射：在索引结构中，存储这个哈希码以及指向对应数据行的指针。
  3. 处理冲突：如果两个不同的值算出了相同的哈希码（哈希碰撞），通常采用链地址法（Linked List）将它们串在一起。

查找过程：
假设执行 SELECT * FROM users WHERE User_ID = 101;

  1. 算法将 101 投入哈希函数，算出哈希值（假设是 7）。
  2. 直接跳到编号为 7 的桶里。
  3. 检查桶里的值。如果桶里只有一个指针，直接取走数据；如果有链表（冲突），则遍历链表找到精确匹配 101 的那一行。

哈希索引的缺陷：

  1. 无法处理范围查询
    在 B+Tree 中，id=1 和 id=2 在物理上是相邻的。但在哈希索引中，由于哈希算法会将连续的值打散，所以可能会出现 1 的哈希值可能是 999，2 的哈希值可能是 12。 假设有 WHERE id > 10 这种查询，Hash 索引完全废掉，必须全表扫描。

  2. 无法利用部分索引键
    如果你建立了一个复合索引 (Name, Age)，B+Tree 可以只用 Name 进行查询（左前缀原则）。而 Hash 索引是将 (Name + Age) 合在一起算哈希值。如果你只提供 Name，算不出之前的哈希值，索引失效。

  3. 无法避免排序
    Hash 索引本身是无序的。如果你执行 ORDER BY，数据库无法利用索引完成排序，必须在内存或磁盘中进行显式排序。

  4. 哈希碰撞重复较多时
    当数据量极大且重复值较多时，大量数据堆积在同一个哈希桶内，查询会退化成 $O(n)$ 的链表遍历，性能剧烈下降。

虽然 MySQL InnoDB 默认用 B+Tree，但它有个聪明的功能叫 Adaptive Hash Index。当 InnoDB 发现某些索引页被频繁访问（热点数据），它会在内存中自动为这些页创建 Hash 索引。 它是数据库自动管理的，你不需要（也无法）手动创建。

聚簇索引

在聚簇索引中，索引的叶子节点直接存储的就是完整的行数据。以上方的数据为例，存在叶子节点上的数据是(1,’Alice’,12)，(2,’Bob’,20)等。每一张表必须有一个聚簇索引，如果表定义了主键，则主键自动成为聚簇索引，如果没有主键，则选择第一个UNIQUE NOT NULL的列作为聚簇索引；如果都没有，InnoDB会创建一个隐藏的row-id作为聚簇索引。

优点：

  • 查询极快： 如果通过聚簇索引键查找，定位到索引就等于拿到了数据，不需要二次查找。
  • 范围查询优势： 因为物理连续，查找 ID 在 1 到 100 之间 的数据效率非常高。

缺点：

  • 插入/更新代价高： 如果插入一个中间值，为了保持物理顺序，数据库可能需要移动大量数据（页分裂）。

非聚簇索引（二级索引）

非聚簇索引的索引结构和实际数据是分开存放的。索引的叶子节点不包含完整的行数据，而是包含索引列的具体数据和一个指向完整数据位置的“指针”（在 InnoDB 中，这个指针通常是主键的值）。还是以上述user表为例，我先给name加上一个索引（idx_name）,叶子节点的存储内容如下：

最后要说明一下联合索引和覆盖索引的区别：

  • 联合索引：是一种“索引结构类型”。比如我们通过CREATE INDEX idx_name_age_city ON user(name, age, city);创建了一个联合索引。
  • 索引覆盖：覆盖索引不是一种索引类型，而是一种“查询现象”或“执行效果”。它表示当前查询所需要的列全部在所使用的索引中，不需要回表。

按逻辑功能分类

普通索引

最基本的索引，没有任何限制。

唯一索引

索引列的值必须唯一，但允许有空值（NULL）。

主键索引

一种特殊的唯一索引，不允许有空值。一张表只能有一个主键。

联合索引（复合索引）：

在数据库表中多个列上共同创建的一个索引，这些列的组合形成一个索引键。

  1. 联合索引满足最左前缀原则；
    假设当前在表中创建了一个联合索引为(name, age, status)
查询条件 是否走索引 原因
WHERE name = ‘Alice’ ✅ 是 匹配最左列
WHERE name = ‘Alice’ AND age = 25 ✅ 是 匹配前两列
WHERE name = ‘Alice’ AND age > 25 AND status = 1 ✅ 是 name 和 age 走索引，status 可能过滤
WHERE age = 25 ❌ 否 跳过 name，无法使用索引（除非是覆盖索引 + ICP）
WHERE status = 1 ❌ 否 完全不匹配最左列
WHERE name LIKE ‘A%’ AND age = 25 ✅ 是 name 走范围，age 可部分使用
WHERE name = ‘Alice’ AND status = 1 ⚠️ 部分使用 name 走索引，status 不走（跳过 age）
  1. 列顺序选择:将选择性高的列,常用查询列靠前；
  2. 索引列不宜过多，通常不超过3-5列，过多列会降低写入性能，增加存储开销；

前缀索引

它只对列值的前面部分字符建立索引，而不是对整个列值建立完整索引。主要用途是在当列值存储的是URL的时候，长文本，hash值的时候。

工作流程：

前置：
假设有一张表 users，其中 email 字段长度为 100，我们对其前 6 个字符建立索引：ALTER TABLE users ADD INDEX idx_email_prefix(email(6))。当你执行 SELECT id, name, email FROM users WHERE email = 'zhangsan@gmail.com' 时，系统的动作如下：

  1. 查找索引树：从 idx_email_prefix 索引树中查找前缀为 zhangs 的记录。
  2. 获取主键：找到匹配 zhangs 的叶子节点，拿到对应的一组 主键 ID。
  3. 回表校验：拿着主键 ID 回到聚簇索引中，取出完整的行记录。
  4. 全值比对：数据库将取出行的完整 email 字段与查询条件 ‘zhangsan@gmail.com‘ 进行对比。
    1. 如果一致，加入结果集。
    2. 如果不一致，丢弃（因为可能存在 zhangs123@xxx.com 这种前缀相同但全称不同的情况）。
  5. 继续检索：回到前缀索引树，看下一个节点是否也是 zhangs，重复上述步骤，直到前缀不再匹配。

优点：

  1. 空间极省：如果原字段 255 字节，前缀索引取 10 字节，索引树的大小会缩减几十倍。
  2. 维护更快：更小的索引意味着更少的磁盘 I/O，插入和更新索引的速度会变快。

缺点：

  1. 即便你只查询 id 和 email，InnoDB 也必须回表。因为前缀索引树里只存了 zhangs，它并不知道完整的 email 到底是不是 zhangsan@gmail.com。为了保险，它必须去聚簇索引里看一眼完整的列值。
  2. 前缀索引也无法用于 ORDER BY 或 GROUP BY 操作，因为索引本身是不完整的，无法保证排序的准确性。

特殊索引

降序索引

默认情况下，大多数数据库（如 MySQL、PostgreSQL、SQL Server）创建的索引都是 B+Tree 升序索引。数据库可以“反向扫描”一个升序索引来获取降序结果，但在处理多列复合排序时，降序索引的优势就会变得不可替代。需要注意的是在 MySQL 8.0 之前，虽然语法支持写 DESC，但引擎实际上会忽略它并创建升序索引。从 8.0 版本开始，降序索引得到了真正的物理支持。

例1：
执行SELECT * FROM table ORDER BY price DESC
数据库通常可以高效地反向读取升序索引。所以对于这种排序情况，专门去创建一个降序索引的收益是很小的。

例2：
执行SELECT * FROM posts ORDER BY publish_date DESC, likes ASC;

  • 创建升序索引 (publish_date ASC, likes ASC)： 数据库无法同时满足这两个方向。它只能先按日期排序，然后在内存中对每一组数据进行昂贵的“文件排序”。这是非常消耗新能的。
  • 创建降序索引 (publish_date DESC, likes ASC)： 索引的物理存储顺序与你的查询需求完全匹配。数据库可以直接从索引中按顺序读取数据，性能极大提升。

所以使用降序索引的时候需要注意两点：

  1. MySQL数据库的版本必须要在8.0以上；
  2. 业务中对某一组查询【查询包含了升序和降序】频繁出现；

索引失效场景

未遵循最左前缀原则

背景：现在有一张表user,其中有a,b,c三列，现在我创建了一个索引index(a,b,c)。
在创建这个索引的时候，数据库会先按 a 排序。在 a 相等的情况下，再按 b 排序。在 a 和 b 都相等的情况下，再按 c 排序。所以会使索引失效的情况有以下几种：

  1. 索引完全失效

以查询1为例，这种情况下并不知道a是多少，所以整个查询就已经乱了，此时查询的时候就只能全表扫描了，从而导致索引失效。查询2和查询3原理都是类似。

    其实创建索引的本质就是拿空间换时间。所以MySQL索引并不是越多越好。索引可以提高查询性能，但它们也会占用更多的存储空间，并且在插入、删除和更新数据时会增加额外的开销，因为索引也需要被更新。过多的索引可能导致性能问题，因为数据库需要更多的时间来维护这些索引。

@NotNull失效
问题背景今天将一个老项目的JDK从8升级到17以后发现所有的校验全部失效了，属性如下。 1234import javax.validation.constraints.NotNull;@NotNull(message = "authType不能为空")private Integer authType; 问题分析查阅资料以后发现，根本原因是 Java EE（Java Enterprise Edition）整体从 Oracle 转移到了 Eclipse 基金会，并更名为 Jakarta EE。由于 Oracle 拥有 “Java” 商标，Eclipse 基金会不能继续使用 javax.* 包名。因此，从 Jakarta EE 9 开始（2020年发布），所有原 Java EE 的 API 从 javax.* 重命名为 jakarta.*。这种问题最容易出现在升级了JDK17以后。 解决方法修改导包路径即可，其他的校验注解的路径也一样。 1import jakarta.validation.constraints.NotNull;
