全局锁

全局锁是一种“重量级”的锁机制。正如其名，它会对整个数据库实例加锁，让整个库处于只读状态。MySQL 提供了一个标准的命令来获取全局只读锁：

当执行这条语句后，很多操作会被阻塞，如 INSERT、UPDATE、DELETE、ALTER TABLE、DROP TABLE、CREATE TABLE。即使事务已经开启，只要涉及写操作，提交时会被阻塞。

执行UNLOCK TABLES或者当客户端断开连接时，全局锁会自动释放。全局锁最经典（也几乎是唯一）的使用场景是进行逻辑备份。为了保证备份出的文件在时间点上是一致的，我们需要确保在备份期间没有任何数据修改。

表级锁

表级锁是一种以整张表为粒度进行加锁的并发控制机制。一旦加锁成功，其他线程对整张表的访问都会受到影响，不存在“只锁部分数据”的情况。这里有一点要注意，表级锁是会话级别，一旦断开连接锁会自动释放。所以表级锁不能跨连接使用的。

基本类型

共享锁（读锁）

特点：

  • 当前会话：只能读，不能写
  • 其他会话：只能读，不能写
  • 允许并发读，禁止任何写操作

使用方式：

排他锁（写锁）

特点：

  • 当前会话：可以读写
  • 其他会话：不能读、不能写
  • 当前会话完全独占

使用方式：

意向锁 (InnoDb独有)

在没有意向锁的情况下，如果事务 A 锁住了表中的某一行（加了行级排他锁），此时事务 B 想要对整张表加表级排他锁（例如执行 ALTER TABLE），事务 B 必须先检查表中的每一行是否已经被锁定。如果表有几百万行数据，逐行检查效率极低。当引入意向锁后。当事务 A 给某一行加锁前，先在表级别插上一面“小旗子”（意向锁）。这样事务 B 想要加表锁时，只需要看一眼表上的“旗子”，就知道能不能加锁了，无需遍历全表。

意向锁由 InnoDB 自动维护，用户无法手动干预。主要分为两种：意向共享锁（IS）、意向排他锁（IX）。下面通过两个例子俩说明这两个锁的作用。

行级锁

行级锁只锁住“被访问的那几行数据”，而不是整张表，他的本质是是对索引记录加锁，如果没有使用索引，可能会退化成“锁全表”。

基本类型

共享锁（S锁）

特点：

  • 他会给某一行或几行加共享锁
  • 其他事务可以再给这几行增加共享锁锁，但是不能加排他锁锁

使用方式：

排他锁（X锁）

特点：

  • 他会给某一行或几行加排他锁
  • 其他事务针对这几行不能在增加共享锁和排他锁

使用方式：

或者

原理分析：

  • A事务在执行select * from xdx_lock where age = 3 for update;的时候发现age没有索引，在 InnoDB（默认 RR 隔离级别）下，优化器只能选择全表扫描，扫描到某一行就对该行加 X 锁，当扫描完整张表，整张表的数据都被加上了X锁，本质上它不是锁表，而是将表中的所有数据都锁住了。
  • 后续所有操作在需要加锁时就发现他们需要加锁的数据都已经被锁住了，所以后续的查询都失败了。

  • 执行select * from xdx_lock where name = 'Alice' for update;后通过name索引查找到name=’Alice’这条记录，查询到该条记录的id=1，再通过回表去主键索引去查询这条记录。此时会将这两条记录全部锁住；
  • 开始B事务的时候，前三条执行成功的原因是，查询的数据和name = ‘Alice’这条数据不重合，所以都没有异常；
  • 当执行select * from xdx_lock where age = 1 for update;时，因为age字段没有索引，所以在查询时只能全标扫描，一行一行读，一行一行加锁，在加锁到name = ‘Alice’的时候，发现这条记录正在持有X锁，而B也要对那一行加X锁，从而就导致了行锁冲突，B被阻塞了。

间隙锁

间隙锁（Gap Lock） 是 MySQL InnoDB 存储引擎在RR隔离级别下，为了解决幻读（Phantom Read问题而引入的一种锁定机制。 简单来说，它锁定的不是具体的记录，而是记录之间的“缝隙”。在数据库索引树中，记录并不是连续紧密排列的。例如，一个索引中有 ID 为 10 和 20 的两条记录，那么 $(10, 20)$ 之间就是一个间隙。其核心目的只有一个：防止其他事务在这些间隙中插入（Insert新数据。

范围判定：间隙锁的范围是左开右开的。假设表中有索引记录：3, 7, 10。可能的间隙区间包括：$(-\infty, 3)$、$(3, 7)$、$(7, 10)$、$(10, +\infty)$ 。间隙锁通常是在非唯一索引或者范围查询中触发。举几个例子来说明一下触发的场景：

  1. 非唯一索引（普通索引）: 当你锁定一条存在的非唯一索引记录时，InnoDB 不仅会锁住该记录（行锁），还会锁住该记录前后的两个间隙。
    例子： 字段 age 有普通索引。执行SELECT * FROM t WHERE age = 24 FOR UPDATE;如果 age 序列是 18, 24, 30。那么间隙锁会覆盖 $(18, 24)$ 和 $(24, 30)$。

  2. 范围查询：对于所有的范围查询（如 > , < , BETWEEN），InnoDB 会对扫描到的区间加锁。

  3. 唯一索引（特例）

  • 如果是等值查询且记录存在：间隙锁会退化为记录锁（因为唯一性保证了不会有重名插入）。
  • 如果是等值查询但记录不存在：依然会产生间隙锁，锁定该值所属的区间。
    举个例子：假设现在表中有id为1，5，9三条数据，但是我想要查询id = 6的数据，由于这条数据不存在，所以直接回锁住(5,9)这个区域。下方两图是我自己验证的结果：

临键锁

简单点说。临键锁其实就是记录锁 + 间隙锁。临键锁的触发是有一定条件的，以下分几种情况来说明：

  1. 唯一索引的“降级”优化
    执行操作：SELECT * FROM test WHERE id = 5 FOR UPDATE;
    结果：只会出发记录锁，只会所著id = 5的这一行数据。
    原因：因为 id 是主键（唯一索引），且 5 这条记录存在。既然唯一，就不可能再插入一个 id=5，所以没必要锁住前后的间隙。InnoDB 自动将其降级为 Record Lock。

  2. 查询不存在的记录
    操作：SELECT * FROM test WHERE id = 7 FOR UPDATE;
    结果： 触发间隙锁，锁定区间 (5, 10)。
    原理： 此时 7 不存在，临键锁退化为间隙锁，防止别人插入 7。

  3. 普通索引（非唯一索引）—— 这是观察临键锁的最佳实验点
    操作：SELECT * FROM test WHERE age = 5 FOR UPDATE; 假设表中的 age 字段是普通索引，数据有 age = 25。
    结果：会锁住 (20, 25] 这个临键锁区间，同时还会为了防止幻读，额外加一个 (25, 30) 的间隙锁。
