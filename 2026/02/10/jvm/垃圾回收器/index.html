垃圾回收器

发表于2026-02-10|更新于2026-10-25|JVM
|浏览量:

JVM 执行引擎里的 GC（垃圾回收器），不是一个“单一模块”，而是一整套内存回收策略 + 算法 + 收集器实现的组合。他的主要职责是

  • 自动回收堆内存中不再使用的对象
  • 避免内存泄漏
  • 控制内存使用效率

回收的主要区域为堆，其次就是方法区中的元空间。

垃圾回收器的种类

Serial GC

工作机制：

  • 单线程
  • 使用 复制算法
  • GC 时 完全 Stop-The-World

执行流程

  1. 停止所有线程
  2. Eden + Survivor 复制到另一块 Survivor
  3. 清空 Eden

Serial GC实现非常简单，并且一般只有单线程的情况下才会使用，所以它也是没有切换线程的开销的。但是缺点也很明显，STW的时间很长，而且现代CPU都是多核的，这种单线程的垃圾回收器基本已没有用武之地。

Parallel GC

Parallel 收集器确实可以被看作是 Serial 收集器的“多线程增强版”。其原理都是和Serial 收集器相同

CMS

CMS（Concurrent Mark Sweep）收集器是 JVM 中一款以“低停顿”为核心目标的老年代垃圾收集器，曾经广泛应用于对响应时间敏感的系统（比如 Web 服务）。它基于标记-清除（Mark-Sweep）算法，并且强调并发执行，尽量减少 Stop-The-World（STW）时间。

CMS 的核心目标只有一个：最小化停顿时间（Low Pause）。
为此做了两件关键设计：

  • 尽量让 GC 线程和用户线程并发执行
  • 避免像压缩算法那样长时间暂停（不做整理，只做清除）

工作流程:

  1. 初始标记：主要是标记 GC Roots 直接关联的对象如【栈引用对象，静态变量，常量池引用等】。即使这个阶段会造成STW，但是速度根块。
  2. 并发标记：从“初始标记”的对象出发，进行 可达性分析，标记所有存活对象。这一步骤是并发执行的，所以用户线程还在创建新对象或者修改引用关系会造成标记的结果不准确。
  3. 重新标记：主要是修正并发标记阶段的“错误”。因为在并发标记的解雇不准确，所以这一步做了增量更新，将存活的对象做一个重新标记。
  4. 并发清除：清除未被标记的对象并回收内存，这一步是与用户线程并发执行。

造成问题：

  1. 内存碎片
    原因：因为CMS在清除完以后是不会做整理的【对象并不移动，就会产生大量碎片】，这样下次如果来了一个大对象，内存就无法存下了会导致OOM。通俗点说就是总容量足够，但连续空间不足。
    解决方法：-XX:+UseCMSCompactAtFullCollection：这个参数告诉 JVM，在不得不进行 Full GC 时，顺便做一次碎片整理。

  2. 并发失败
    原因：CMS 是“边回收边运行”的，如果老年代回收速度 < 对象产生速度，这会导致老年代还没清完，就满了。解雇就会触发JVM的serial Old【单线程的Full GC，会STW，而且过程会非常慢】

  3. 浮动垃圾
    原因：在并发标记阶段，该对象是存活的，但是在清理阶段，该兑现成了垃圾，此时CMS就不会去回收它。

G1 GC

G1 GC不同于传统的收集器，它会将把整个堆分成约2048 个大小相等且独立的小方格称为 Region。虽然逻辑上依然有 Eden、Survivor、Old 的概念，但它们不再是物理连续的，而是分散在不同的 Region 中。除此之外还多了一个 Humongous 区域，专门用来存放大对象（超过 Region 一半大小的对象）。
内存布局：
G1 打破传统 “新生代 / 老年代物理连续” 的布局，将整个堆划分为多个大小相等的独立 Region（默认 1MB～32MB，2 的幂，最多 2048 个，由 -XX:G1HeapRegionSize 指定）。

  1. Region 类型（逻辑分代，动态切换）
    Eden Region：新生代，存放新对象，GC 时清空。【上图中红色区域】
    Survivor Region：幸存区，存放 Eden GC 后存活对象，默认 1～2 个。【上图中红色区域中带S字母的】
    Old Region：老年代，存放长期存活对象（如晋升的 Survivor 对象）。【上图中蓝色区域】
    Humongous Region：大对象区，存放超过 Region 50% 大小的对象，由连续 Region 组成，避免跨 Region 存储。【上图中蓝色区域带H字母的】

  2. 关键数据结构
    Remembered Set（RSet，记忆集）：每个 Region 对应一个 RSet，记录其他 Region 指向当前 Region 的引用，用于跨代回收时快速扫描根，避免全堆扫描。例如：当前有一个Region X，如果每次垃圾回收的时候都扫描一遍哪个region和他有关联的话会造成很长时间的停顿，堆越大，region会越多，就会导致STW停顿时间更长，当维护了Rset之后，在回收 Region X 时，只需要看 X 自己的 RSet，RSet 里已经记好了：哪些其他 Region 有引用指向 X。GC 只需要扫描这几个被记录的外部 Region 就行，不用全堆扫描。
    Collection Set（CSet，回收集合）：每次 GC 选定的待回收 Region 集合，优先选垃圾最多的 Region，是 Garbage First 的直接体现。

工作流程：

  1. Young GC
    这个阶段类似传统 Minor GC，回收 Eden + Survivor，晋升的逻辑也是一样，达到条件以后对象晋升到 Old，在这个阶段会STW【只回收年轻代 Region，所以速度非常快】。

  2. 并发标记
    这是 G1 的核心阶段，用来找出哪些 Old Region 垃圾最多，分为以下几个子阶段：

  • 初始标记：标记 GC Roots 直接引用，这个阶段会STW。
  • 根区域扫描：扫描 Survivor → Old 的引用，这个步骤是并发执行。
  • 并发标记：标记整个堆的存活对象，这个阶段是多线程并发执行。
  • 重新标记：修正并发阶段遗漏的标记（类似 CMS），这个阶段会STW。

  1. Mixed GC
    这个是G1 最核心的阶段，回收内容包括所有 Young Region 和一部分 Old Region（垃圾最多的）。在清理阶段不一次回收全部 Old（避免长停顿），而是分多次逐步清理 Old，这个阶段会STW，但是暂停时间会很短。

  2. Full GC（极端情况）
    G1 在正常设计下不会频繁 Full GC，但在内存不足、晋升失败或并发回收跟不上时，会触发 Full GC 作为兜底手段。在G1中它通常是单线程、整堆整理、压缩整理内存，这个阶段会STW，而且非常慢（可能秒级甚至更高）。

Garbage-First:
G1 GC不是像传统收集器那样“按代（新生代 / 老年代）整块回收”,而是基于Region来回收，优先回收高收益 Region。

  1. 优先级计算
    G1 后台统计每个 Region 数据，基于以下数据，维护优先级列表，每次 GC 优先选垃圾最多、回收最快、收益最高的 Region 加入 CSet。
  • 垃圾占比：可回收垃圾 / Region 总大小。
  • 回收耗时：历史回收该 Region 的平均时间。
  • 存活对象密度：存活对象越少，回收收益越高。
  1. 回收逻辑
  • 传统 GC：回收整个新生代或老年代，停顿随代龄增大而变长。而G1只回收 CSet 中的高收益 Region，控制 CSet 大小以匹配目标停顿时间，实现 “按需回收、收益最大化”。
  • G1（Garbage First）：只回收 CSet 中的高收益 Region，控制 CSet 大小以匹配目标停顿时间，实现 “按需回收、收益最大化”。

染色指针

一般情况下普通指针是0x1000，但是ZGC的指针是0x1000 + 状态位，这个状态位是告诉 JVM：

  • 这个对象是否被标记
  • 是否已经移动
  • 是否需要修复

这样 JVM 在“读的时候”就能判断要不要去查转发表。

内存布局

ZGC 的内存结构核心是ZPage 分区 + 染色指针 + 多重映射，JDK 21 后新增分代（年轻代 / 老年代），整体无固定 “代” 的物理隔离，全堆统一管理但按对象大小分三类 ZPage。如下图：

年轻代：默认占堆 60%，小 / 中 ZPage 为主，高频回收（复制算法）。
老年代：默认占堆 40%，中 / 大 ZPage 为主，低频回收（标记 - 复制）。
ZPage：内存基本单元，动态创建 / 销毁，分小 / 中 / 大三类，与 G1 固定 Region 不同。

类型 大小 存放对象 回收策略
小页面 2MB ≤256KB 优先并发回收
中页面 32MB 256KB ~ 4MB 按需并发回收
大页面 ≥4MB（2MB 倍数） ≥4MB 仅无引用时回收，不移动
