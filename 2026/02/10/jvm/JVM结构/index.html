JVM结构

发表于2026-02-10|更新于2026-10-25|JVM
|浏览量:

JVM（Java Virtual Machine）是 Java 跨平台特性的核心。简单来说，它是一个翻译官，负责将字节码（.class 文件）解释或编译成特定操作系统的机器码。

JVM构成

类加载子系统

它主要是把.class字节码文件加载进内存，并转换为 JVM 可运行的数据结构。类加载子系统主要包含三大部分：类加载器、类加载过程和双亲委派机制，下面一一介绍。

类加载器

类加载器主要负责读取字节码文件并将其转换为 Class 对象，随后存入方法区，最终在堆中生成对应的 java.lang.Class 对象。JVM 内置三大类加载器分别是：

  1. 启动类加载器（Bootstrap ClassLoader）：它是用 C++ 实现，属于 JVM 内核一部分但它不是 Java 类并且不继承 ClassLoader。它通常用来加载核心基础库如：java.lang.*、java.util.*等。
    验证:
  1. 扩展类加载器（Extension / Platform ClassLoader）:Java 标准扩展库（Standard Extensions）不是最核心类（由 Bootstrap 加载），但属于 JDK 扩展功能的类。
  • 在JDK8及以前使用的是 Extension ClassLoader 其默认加载目录$JAVA_HOME/lib/ext下的类；例如：javax等。
  • 在JDK9以后使用的是Platform ClassLoader，它负责加载标准平台模块（非核心模块）。例如：java.sql、java.xml等。
  1. 应用程序类加载器（Application ClassLoader）:这个就是最常见的加载器。平时我们自己写的代码，第三方jar包中使用的加载器都是这个。

类加载过程

类从被加载到可用，要经历 5 个阶段：加载 → 验证 → 准备 → 解析 → 初始化。

  1. 加载：通过全限定名查找 .class 文件，并生成 Class 对象。
  2. 验证：检查字节码是否符合JVM规范。
  3. 准备：为静态变量分配内存并设置默认值。举个例子：static int a = 10;在准备阶段将会给a赋初始值：a = 0【这里要注意赋的是初始值，并不是代码里的值】。
  4. 解析：将符号引用转换为直接引用（如方法调用）。
    符号引用 = 模糊的描述(如”调用User.getName()”)
    直接引用 = 具体的内存地址(如”0x1234内存处的方法代码”)
    转换过程 = JVM第一次执行时把”文字描述”变成”具体地址
  5. 初始化：执行静态代码块（static{}）和静态变量赋值。举个例子：static int a = 10;在初始化阶段将会给a赋值：a = 10。
    初始化触发时机：
    • 使用 new 创建对象
    • 访问静态变量
    • 调用静态方法
    • 反射Class.forName()
    • 初始化子类【子类初始化时会先初始化父类】

为什么需要双亲委派机制？

  1. 安全性：防止核心类被篡改。
    如果没有双亲委派，任何开发者都可以编写一个名为 java.lang.String 的类并放在自己的项目里。如果 AppClassLoader 直接加载了这个“假 String”，在这个假类里写上 System.exit(0) 或者窃取密码的代码，整个 JVM 就会崩溃或泄密。
  2. 唯一性：避免“同名不同类”
    通过“向上委派”确保了同一个类只会被最高层的那个加载器加载一次，保证了类在程序中的唯一性。
  3. 层次化：明确职责边界
    这种机制建立了一种清晰的优先级层级，核心类交给最权威的 Bootstrap 加载。扩展功能交给 Extension 加载。用户代码：交给 Application 加载。这种结构使得 Java 虚拟机在运行之初就拥有了一个稳固的基础（由顶级加载器构建），而用户自定义的代码只能在这个坚实的基础上进行扩展，而不能动摇根基。

运行时数据区

Java 虚拟机（JVM）在执行 Java 程序的过程中，会把它所管理的内存划分为若干个不同的数据区域。这些区域各有各的用途，有的随着 JVM 启动而创建，有的则随着线程的启动和结束而建立和销毁。运行时数据区主要分为五个部分。

堆

特点

  1. 堆是JVM中最大的一块内存区域，专门用来存放对象实例和数组。你可以把它想象成一个”对象仓库”，所有通过new关键字创建的对象都会存放在这里。
  2. 堆是所有线程共享的，因此多线程访问堆中的对象时需要考虑线程安全问题。
  3. 堆是可以进行动态扩容的，它也是垃圾收集器管理的主要区域。

内存结构

堆在逻辑上分为新生代和老年代【老年代一般占堆内存的2/3，新生代占1/3】，新生代的区域又会分为伊甸园区（Eden)和幸存者区S0,S1【空间分配：Eden：S0：S1 = 8:1:1】。

对象在堆中的生命周期

  1. 当创建新的对象时，判断当前对象是否为大对象？直接进入老年代：在伊甸园区分配内存。
  2. 当Eden中的空间不足时会触发新生代的Minor GC，他会将Eden和S0区中存活对象复制到S1区，经过此过程复制的对象年龄+1，然后清空Eden和S0，并将S0和S1区域的名称调换；
  3. 在复制过程中,
    • 如果对象年龄达到阈值（默认15），对象晋升到老年代；
    • 如果S1区已满，会触发担保机制，会判断当前老年代中是否能放得下该对象，如果能放的下直接放到老年代中，如果放不下先触发Full GC，再判断老年代中是否能放下该对象，如果还是放不下则会抛出OOM的错误。
  4. 当老年代的存储空间已满时会触发Full GC；
  • 大对象的定义
    在JVM中有一个参数-XX:PretenureSizeThreshold用来定义多大的对象为大对象。默认情况下该值为0。例如：设置 -XX:PretenureSizeThreshold=3145728（即 3MB）那么任何大于 3MB 的对象（如超大字节数组）都会跳过新生代，直接降临在老年代。但是要注意，这个参数只对 Serial 和 ParNew 两款收集器有效。如果你使用的是现代主流的 G1 或 Parallel Scavenge，这个参数是不起作用的。对于G1收集器来说，只要对象的大小超过了 Region 大小的 50%，它就被判定为 Humongous Object（巨型对象）。这些对象会直接存放在特殊的 Humongous Region 中（逻辑上属于老年代）。可以通过 -XX:G1HeapRegionSize 设定（1MB - 32MB 之间，且为 2 的幂）。

常见问题

  1. 内存泄漏
    对象在程序中不再被使用，但因为仍然被某些存活的对象引用，导致 GC 无法回收它们。随着时间推移，可用堆空间越来越少。举个例子：程序员定义了一个 static List 来做缓存，但在用户退出登录时忘记从 List 中 remove 掉用户对象。这种情况下就会造成静态集合累积。

  1. 内存溢出（OOM）
    堆内存已经达到设定的最大值（-Xmx），且经过 Full GC 后依然无法支撑新对象的分配。一般造成OOM的情况有一下几种：

    1. 内存泄漏的终点：积累到一定程度导致 OOM。
    2. 突发大对象：一次性加载了超过堆容量的数据。
    3. 参数配置不当：业务量增长，但堆内存设置过小。

举个例子：某个导出功能需要将数据库中 100 万条订单数据转换成 Excel。如果不使用流式处理，而是尝试把这 100 万个 POJO 对象全部 load 到一个 List 里，会瞬间撑爆堆空间。

  1. 频繁 Full GC

JVM 花费了 98% 以上的时间在做 GC，但只回收了不到 2% 的内存。这会导致“Stop The World”（STW），程序表现为严重的“假死”。造成这种问题的原因一般是对象晋升过快，大量对象在新生代中还没有待够时间就进入了老年代，从而频繁触发老年代的Full GC,而Full GC是很消耗性能的一种垃圾回收机制，从而会使系统每隔几秒就卡顿一次。出现这种情况的例子一般是新生代的区域过小导致，有些对象还没有来的及被Minor GC回收就因为担保机制直接进入了老年代。

方法区

方法区（Method Area）是 JVM 中一个非常核心的逻辑区域，它与堆一样，是所有线程共享的内存区域。如果把堆比作“存放对象的仓库”，那么方法区就是“存放图纸和规则的档案室”。根据 JVM 规范，方法区主要存储以下三类信息：

  1. 类型信息：类的全限定名、父类全限定名、修饰符、实现的接口列表。
  2. 字段与方法信息：字段名、类型、修饰符、方法名、返回类型、参数列表、字节码指令、异常表。
  3. 运行时常量池：这是方法区的一部分。编译期产生的各种字面量（如字符串常量）和符号引用在类加载后会存放在这里。每一个 Java 类编译后都会产生一个 .class 文件。这个文件里有一块区域叫 Constant Pool Table（常量池表）。与之相对的就是静态常量池，存的是字面量（如字符串、被 final 修饰的数值）和符号引用（类名、方法名、参数类型）。当我们在代码里面对某一个常量写了多次，如果我们对该常量保存多次显然时不合理的，为了方便复用，所以创建了一个运行时常量池。
  4. 虚方法表：【详细见虚方法表】

方法区的实现

  1. JDK 7 及以前：永久代
    永久代其实就是堆里面的一部分区域，但是这个区域在JDK 7前后发生了一些变化。
  • 在JDK 7以前，堆像个大仓库，专门放 new 出来的对象。垃圾回收（GC）非常频繁。永久代像个保险柜，放类信息、常量、静态变量。它的大小是固定的，GC 几乎不怎么管它。如果程序里产生大量的字符串（比如 intern() 方法调用过多），永久代的专属空间很快就满了，直接报 OOM: PermGen space，但此时堆中明明还有很多空位。
  • 在JDK 7后，为了提高内存利用率，JVM 开发团队决定把字符串常量池和静态变量从“保险柜”搬到“大仓库”（堆）里。这样它们就可以利用堆内存的自动扩容机制，并且能更频繁地被 GC 回收，极大地减少了 OOM 的风险。
  1. JDK 8及以后：元空间 【需要详细拿一张说明】
    元空间不再占用 JVM 内存，而是直接使用本地内存。只要本地内存足够，就不会触发 OOM。默认情况下，元空间的大小仅受限于操作系统的实际可用内存。

栈

栈是线程私有的一块内存区域，它用于存储方法执行时的各种数据。每个线程创建时都会创建一个对应的虚拟机栈，线程结束时栈也会销毁。栈有以下几种特点：

  1. 线程私有：每一个线程都有自己的栈，线程之间是不共享的；
  2. 生命周期和线程保持一致：当线程被创建的时候，栈便创建；当线程销毁时，栈销毁；
  3. 存储方法执行数据：每次方法调用都会创建一个栈帧；
  4. 遵循先进后出原则；

JVM中的栈分为两种：JVM虚拟机栈和本地方法栈。这两种栈的结构和工作方式都非常相似，不同在于他们的服务对象不同，JVM虚拟机栈用来给Java方法提供服务，本地方法栈是为给 JNI（Java Native Interface）使用，比如调用 C / C++ 方法。

栈帧是栈中的基本单位，每一个方法的调用直到执行完成的过程，就对应着一个栈帧在虚拟机栈中入栈到出栈的过程。

  • 符号引用： 仅仅是一个字符串字面量，比如 com.example.Service.order()。它描述了目标，但不知道目标在内存的哪个位置。

栈问题

  1. 内存溢出错误 (StackOverflowError)
    这是最常见的栈问题。当线程请求的栈深度超过了 JVM 允许的最大深度时，就会抛出 java.lang.StackOverflowError。

造成原因：

  • 无限递归： 方法自己调用自己，且没有正确的退出条件。
  • 深度递归： 递归层次过深，超过了默认栈容量。
  • 方法调用链过长： 比如过度的 A -> B -> C… 这种调用关系。

解决方法：

  • 检查递归逻辑，确保有终止条件。
  • 通过 -Xss 参数增大栈空间（例如 -Xss1m）。

tips:
-Xss:
X：代表这是一个非标准参数（Non-standard Option），虽然大多数 JVM 都支持。
s：代表 Stack（栈）。
s：代表 Size（大小）。

可以把栈想象成一个物理容器，-Xss 决定了这个容器的高度。

  • 如果值调大： 每个线程能容纳的方法调用深度（递归深度）就更深，减少 StackOverflowError 的概率。
  • 如果值调小： 单个线程占用的内存变少。在内存总量一定的情况下，系统可以创建更多数量的线程。
  1. 内存溢出错误 (OutOfMemoryError)
    这里的 OOM 与堆内存溢出不同，它通常发生在创建新线程的过程中。

造成原因：

  • 无法分配原生内存： 操作系统无法为新线程分配足够的原生内存作为栈空间。
  • 线程创建过多： JVM 尝试创建数万个线程，导致耗尽了操作系统的资源。

解决方法：如果是因为线程创建过多而导致 OOM，解决方法往往是减小 -Xss 的值。因为内存总量有限，每个线程占用的栈越小，理论上能创建的线程就越多。

2: return

PC 指向哪一条，就取哪一条。

  1. 解码
    将字节码转换为 JVM 内部可识别的操作。

比如：

  • aload_0 → 加载局部变量 0
  • invokevirtual → 调用实例方法

  1. 执行
    执行对应操作，例如： 入栈 、出栈 、方法调用 、数学运算

  2. 更新 PC
    执行完当前指令后，PC 自动指向下一条字节码。

  3. 循环执行
    不断重复上述操作 直到方法结束。

JIT 编译器

JIT 编译器（Just-In-Time Compiler）是 JVM 执行引擎里最“提速”的核心组件，它的作用是把“正在运行的热点字节码”实时编译成机器码，让后续执行直接跑CPU指令，而不是逐条解释。

JVM 并不是一启动就编译所有代码（因为编译耗时且占内存）。它通过热点探测来决定何时触发 JIT：

  • 方法调用计数器： 统计方法被调用的次数。
  • 回边计数器： 统计循环体代码执行的次数（用于触发 OSR，On-Stack Replacement，即在循环进行中直接替换为优化后的代码）。

当计数器超过设定的阈值（由 -XX:CompileThreshold 参数控制），就会触发 JIT 编译。

编译器名称 别名 特点
Client Compiler C1 编译耗时短，只进行简单的局部优化
Server Compiler C2 编译时间长，但会进行全局深度优化，性能极高

分层编译（Tiered Compilation）
现代 JVM（Java 8 及以后）默认开启分层编译。它将执行分为 5 层：

  1. 第 0 层： 解释执行。
  2. 第 1-3 层： C1 编译，提供不同程度的优化。
  3. 第 4 层： C2 编译，进行极致优化。
